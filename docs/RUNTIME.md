# Arsenkin MCP

Самостоятельный MCP для Arsenkin: 11 исходных инструментов, API-адаптер,
оценка и согласование платных запросов, очередь, batch, polling и отмена.
Запускается без AI Kit и `mcp_platform`. С версии 0.2.0 доступен экспорт сохранённых результатов;
подключение к своему аккаунту выполняет оператор.

## Установка

Python 3.12–3.14. Источники описаны в `SOURCE_PROVENANCE.json`, исходный
контракт закреплён в `contracts/arsenkin.json`.

```sh
uv sync --frozen --extra standalone
uv run python scripts/verify.py
uv build
uv run arsenkin-mcp --transport stdio
```

Wheel: `pip install './dist/zai_arsenkin_mcp-0.5.0-py3-none-any.whl[standalone]'`.
Extra `standalone` закрепляет FastMCP 3.4.4. Базовый wheel содержит код адаптера,
инструментов и выполнения для композиции в платформе; версию FastMCP хоста
он не меняет. Remote пока не настроен. Для точного воспроизведения wheel
используйте LF checkout (`core.autocrlf=false`) закреплённого SHA.

## Настройка и доступ

Переменные приведены в `.env.example`; приложение не загружает dotenv само.
`ARSENKIN_TOKEN_FILE` указывает на файл API-токена. Без токена API и worker
отключены, локальная оценка и подготовка согласований доступны.
Credentials не приходят от MCP-клиента. На POSIX файл секрета должен быть
доступен только владельцу; на Windows ограничьте ACL секретов и каталога SQLite.

Stdio использует доверенного оператора `ARSENKIN_LOCAL_PRINCIPAL` и серверные
`ARSENKIN_LOCAL_SCOPES`. HTTP требует `ARSENKIN_MCP_PUBLIC_KEY_FILE` с RSA public key:

```sh
uv run arsenkin-mcp --transport http --host 127.0.0.1 --port 8815
```

Endpoint `/mcp` принимает RS256 JWT с `sub`, будущим `exp`, совпадающими
`iss`, `aud`, `account_id`; scopes — `arsenkin:read` и `arsenkin:execute`.
JWT не увеличивает бюджет. Сервер, CLI согласований и worker одного аккаунта
должны использовать общий `ARSENKIN_STATE_PATH` и одинаковую конфигурацию.
Отдельные SQLite-журналы одной платной credential не объединяют лимиты
и защиту от повторов; используйте один журнал на аккаунт.

## Проверка обновлений

`arsenkin_check_update` сравнивает установленную версию с последним релизом на GitHub
и только предлагает команду обновления; сам MCP ничего не устанавливает. При запуске
сервер (stdio и HTTP) в фоне обращается к `api.github.com` — анонимный GET не чаще
раза в сутки, — если не задан `ARSENKIN_DISABLE_UPDATE_CHECK=1`; учитывайте это
для серверных развёртываний с ограниченным исходящим трафиком. Результат хранится
в `update-check.json` рядом с `ARSENKIN_STATE_PATH`. После неудачного запроса
повтор выполняется не раньше чем через 30 минут, а `force_refresh` — не чаще
раза в минуту. Принимаются только теги вида `v1.2.3`; любые другие отбрасываются.

## Платные задания

По умолчанию действуют ручное согласование и нулевые месячные лимиты.
Задайте положительные principal/account лимиты. Prepare выдаёт согласование
на точный hash, владельца и оценку с TTL 30 минут. Оператор принимает его:

```sh
uv run arsenkin-approval UUID --principal local-operator --request-hash SHA256
```

Submit с теми же аргументами и idempotency key ставит задание в очередь.
Принятие не является MCP-инструментом. Расходование согласования, резерв
бюджета, проверка повторов и создание задания атомарны в SQLite.
Повтор точного approval/key возвращает то же задание; другой approval/key
или пересекающийся оплаченный hash отклоняется даже для другого пользователя
аккаунта и после завершения/отмены. Lookup показывает только данные владельца.
Неполный индекс старого batch блокирует новые оплачиваемые запросы.

Стоимость выражена в условных единицах исходной модели, не в рублях.
`ARSENKIN_MAX_COST_PER_APPROVAL=0` означает отсутствие дополнительного потолка
на одно согласование; месячные лимиты ручной политики сохраняются.
Оператор может явно включить `ARSENKIN_AUTO_PAID_POLICY=unlimited`: prepare
создаёт типизированное серверное согласование standing policy. Эта политика
обходит месячные финансовые ограничения, сохраняя положительный потолок
согласования, очередь, частоту, idempotency и аудит. По умолчанию она выключена.

```sh
uv run arsenkin-worker
uv run arsenkin-worker --once
```

Worker отдельно обрабатывает постоянную очередь. Явный batch объединяет
совместимые запросы и сохраняет `client_ref` и ID каждой группы. Автоматическое
объединение нескольких отдельных jobs остаётся функцией центрального worker;
самостоятельный worker выполняет такие jobs отдельно.

До платного POST worker повторно проверяет текущую политику и бюджет месяца,
получает владение заданием и фиксирует намерение отправки. Task ID сохраняется
до возврата к обработчику; сбой следующей записи не стирает известные ID.
Неоднозначный ответ или падение при отправке дают `submission_outcome_unknown`
без повторного POST и без возврата резерва; нужна ручная сверка с провайдером.
Известные ID после перезапуска продолжают polling. Отмена до отправки возвращает
резерв; после известной или неопределённой отправки резерв сохраняется.
SQLite и внешнее API не являются одной транзакцией.

Частота и параллельность учитываются на каждую HTTP-попытку в общем журнале.
Платный POST автоматически не повторяется; read-retries учитываются отдельно.
Retry-After и cooldown переживают перезапуск. Вызовы имеют общий deadline;
после отмены клиентского запроса не остаётся фонового API-вызова.

## Изменения проектов (opt-in)

Набор `projects_write` (`arsenkin_projects_write`, scope `arsenkin:execute`) выключен по
умолчанию и удаляется `ARSENKIN_READ_ONLY=1`. Каждое изменение требует одноразового
согласования на точный запрос и того же principal: оператор принимает его через
`arsenkin-projects-approval` (файл `<имя БД>.projects-approvals.json` рядом с
`ARSENKIN_STATE_PATH`, свой для каждой БД состояния, TTL 30 минут). Согласование привязано к
аккаунту (account id, отпечаток токена, URL провайдера, БД состояния). Ожидающих согласований не
больше 10 на principal и 100 всего, запрос до 2 МиБ, файл до 8 МиБ (`approval_quota_exceeded`).

Использованное согласование становится записью отправки. Повтор с тем же `approval_id` не
вызывает провайдера: завершённая запись возвращает сохранённый результат. Если запрос ушёл, а
ответ потерян (таймаут, обрыв, невалидный ответ), инструмент возвращает `outcome_unknown`
(без retry), и новое согласование на тот же запрос отклоняется, пока оператор не проверит
провайдера и не выполнит `arsenkin-projects-approval --approval-id ID --resolve applied|not_applied`.

Платный `run_positions` **не учитывается** в месячных бюджетах
(`ARSENKIN_PRINCIPAL_MONTHLY_COST_LIMIT`, `ARSENKIN_ACCOUNT_MONTHLY_COST_LIMIT`) и в
`ARSENKIN_MAX_COST_PER_APPROVAL`, не резервирует стоимость и не проходит через очередь выше.
Его ограничивают только `ARSENKIN_PROJECTS_PAID=on` (по умолчанию выключено) и одноразовое
согласование оператора; так решил владелец.

## Подключение и проверка

Платформа устанавливает конкретный базовый wheel по версии и SHA-256.
В ней остаются auth/scopes, центральный store, approval, аудит, квоты,
очередь, автоматические micro-batches и эксплуатационные маршруты.
Самостоятельная SQLite используется только при отдельном запуске сервиса.

Тесты используют синтетический HTTP и временные SQLite: 11 исходных схем и экспорт результатов,
согласования, ownership, budget-races, повторные hashes, восстановление,
batch lineage, отмену, Retry-After, JWT, stdio и HTTP. Реальные платные API,
production и контейнерный запуск не являются частью offline-проверок.
